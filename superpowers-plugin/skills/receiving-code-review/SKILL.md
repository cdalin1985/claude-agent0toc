# Receiving Code Review

## Overview

Review feedback is data, not judgment. Use it to improve code and grow as an engineer.

**Core principle:** The code is being reviewed, not you.

## Response Patterns

### Agree and Update
- Make the change
- Thank reviewer briefly
- No long explanation needed

### Disagree Respectfully
- Explain your reasoning
- Provide evidence (benchmarks, examples)
- Ask "what would change your mind?"
- Be open to being wrong

### Need More Info
- Ask specific questions
- Show what you tried
- Reference the code in question
- Avoid going in circles

### Defer to Different Conversation
- "Good point - file as follow-up?"
- "Out of scope for this PR"
- "Let's discuss the larger refactor separately"

## How to Read Feedback

### Look for Patterns
- Multiple comments on same thing? Real issue.
- Reviewer keeps asking questions? Code unclear.
- Many "nits"? Probably style preferences.

### Distinguish Severity
- **Must-fix**: Bugs, security, broken patterns
- **Should-do**: Better approaches, clarity
- **Nice-to-have**: Style, minor improvements
- **Personal preference**: Acknowledge, don't always change

### Don't Take it Personally
- Reviewer wants the code better
- Critique is about the artifact, not you
- Disagreement is healthy

## Anti-Patterns

- Defensive responses
- Long explanations to avoid changing code
- Ignoring feedback you disagree with
- Making all changes without thinking
- Arguing every comment
- "Will do" without doing

## After the Review

- Address all comments (change or respond)
- Re-request review when ready
- Learn the patterns for next time
- Thank reviewer if they did good work
